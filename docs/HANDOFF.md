# 开发交接

## 先了解运行链路

`index.html → app.js → resolveRoute → createViews → 写入 DOM → bind → mountSculpture`。

`app.js` 负责应用生命周期和可变状态；每次页面渲染先停止动画并销毁旧场景，再生成 HTML 和注册事件。`views.js` 只读取传入的状态快照并生成 HTML，不写入存储、不绑定事件。模板通过同一快照共享组件，应用层的视图包装函数保证事件触发时读取最新状态。

`core` 放置与具体页面无关的路由、DOM 和存储能力。`data` 是示例内容。`rendering` 管理 Three.js、模型读取和降级转台。导入路径按发布布局组织；浏览器应通过开发服务或 dist 运行，不直接打开 src/index.html。

## 常见修改步骤

- 改商品：编辑 catalog；数组索引同时对应模型编号，新增时必须提供模型和全部预览帧。
- 加页面：在 views 添加模板，在 app 的 render 映射登记，在 router 的白名单中登记，按需添加导航与事件。
- 改交互：在 app 的 bind 中定位对应元素 ID 或 data 属性；DOM 每次替换后都会重新绑定。
- 改模型：先备份 public/assets，执行原 Python 工作流；脚本现在写入 public/assets，再运行 build。
- 发布：执行 check、test、format:check、build，推送 main 后 GitHub Actions 自动发布 dist 到 GitHub Pages；PR 只检查。详见根目录部署说明。

## 数据约定

继续使用 `nitu-app-cart`、`nitu-app-addresses`、`nitu-app-orders`、`nitu-app-favorites`，不做清空或迁移。收藏记录商品索引，购物车项为 `{id, qty}`，订单包含 items 和地址快照。地址信息只保存在当前浏览器。

保留旧版本存储语义：无值或 JSON 损坏时回退默认值，但尚未引入完整数据结构校验，存储空间满时的写入异常也未处理。生产化时应另设迁移和异常提示，不能直接把演示订单当作真实订单使用。

## 验收清单

自动检查覆盖语法、本地模块引用、路由边界、原版页面 HTML 回归和缓存壳资源完整性。修改模板后需有意识地更新回归基线，不要直接接受意外差异。

人工验收：三个模型切换 → 制作播放、暂停、拖动 → 商城筛选与搜索 → 收藏 → 加购、数量和移除 → 新增及编辑测试地址 → 提交模拟订单 → 模拟支付 → 刷新确认持久化。另在真实手机上测试 WebGL、双指缩放、添加主屏幕以及离线重开。

## 后续仍需处理

本次整理保持现有技术栈。app 仍集中管理事件和可变状态，views 仍采用字符串模板；进一步拆成独立功能控制器时，应先增加交互级浏览器回归。三维加载的异步竞态、资源释放、存储数据结构校验、真实设备性能和离线更新策略需要单独评估。当前没有账号、库存、支付、真实传承人数据或服务端同步。

构建会清理 dist 并复制 src/public；产物内容哈希作为 PWA 缓存版本，缓存按注册作用域隔离。删除的资产不会残留。
